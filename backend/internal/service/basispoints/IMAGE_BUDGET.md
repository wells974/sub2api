# BPS 图片预算与历史恢复（第二批）

第二批复用现有图片准入、上传、compact、用量累计及 Redis CAS，不引入新的转发流程。第一批的观测说明见 [OBSERVABILITY.md](OBSERVABILITY.md)。

## 配置与启用

为减少二开与上游配置 DTO、前端设置页面的冲突，本批使用独立的**后端进程环境变量**，不新增后台表单或数据库迁移。

| 环境变量 | 默认 | 作用 |
| --- | --- | --- |
| `SUB2API_BPS_NATIVE_IMAGE_TOTAL_MIB` | `32` | 每个原生图片请求窗口的解码后总量，允许 1–512 MiB；不会继承已有的中转总量配置 |
| `SUB2API_BPS_IMAGE_BYTE_COMPACT` | `false` | 已有图片策略为 `auto_compact` 时，在占用达到总预算的 75% 后尝试提前压缩 |
| `SUB2API_BPS_TRIM_OLD_TOOL_IMAGES` | `false` | `auto_compact` 遇到历史前缀本身超限时，允许裁剪已完成历史工具结果中的旧内联截图 |

推荐第一步保持 32 MiB，仅启用按字节提前压缩；旧截图裁剪需要明确接受旧视觉信息丢失后再开启。示例：

```sh
SUB2API_BPS_NATIVE_IMAGE_TOTAL_MIB=32
SUB2API_BPS_IMAGE_BYTE_COMPACT=true
SUB2API_BPS_TRIM_OLD_TOOL_IMAGES=false
```

同时把现有后台“图片限制策略”设为 `auto_compact`。变量需要传给后端进程；Docker 的 `.env` 文件本身不会自动把变量注入容器，需通过部署的 `environment` 或 `env_file` 传入。所有服务实例应保持一致，修改部署变量后重启实例。

两个新开关关闭、原生预算保持默认且没有既有 v2 状态时，直接复用未修改的原图片策略。原按张数触发仍有效，也保留原来的合并上传字节限制、错误文案和旧状态 key；不会因为本批上线而自动扩大为两个窗口的预算。下文的分区预算是显式启用扩展后的行为。

75% 是本地提前处理阈值，不是上游约束。首轮没有可压缩历史、且本轮本身仍在硬预算内时，直接发送，不因达到提前阈值而拒绝。自动 compact 继续要求兼容 Codex 客户端和稳定会话身份；新策略不会为匿名会话猜测跨轮边界。

原生单图仍限制 20 MiB。中转单图及总量继续使用原有后台配置。提高本地总量不保证上游接受更大的窗口，也不会改变请求体、并发内存、临时存储、像素数等其他保护。环境变量非法时，BPS 请求返回设置不可用，不默默放宽限制。

## 实际处理顺序

1. 保持原始 HTTP 请求体大小和并发内存准入。
2. 识别历史，按顺序重放已有裁剪/压缩检查点。
3. 判断有效历史的张数和内联图片字节是否需要处理。
4. 使用已有 `ImageHistory.Split` 确定历史与本轮的边界；优先按原样压缩历史。
5. 分别验证历史压缩窗口和本轮窗口的数量、单图及总量。
6. 用原有原生/中转图片流程完成完整媒体校验和上传。
7. 压缩结束后，再验证“上游实际保留的窗口 + 本轮原始图片”的预算；不足则停止生成，保留已经发生的压缩用量。
8. 保存检查点并继续原有生成流程。

例如 32 MiB 预算下，旧历史 22 MiB、本轮 13 MiB 合计 35 MiB，但两次实际请求都可以在各自预算内发送；不再先用 32 MiB 拒绝两段的组合。上传计划可以包含最多两个已分别检查的窗口，但任何实际生成/压缩窗口都不能借此突破单窗口预算。重复图片按出现次数计入预算；上传缓存与去重保持原样。

无法识别边界、本轮本身超限、历史中受保护的图片无法容纳、或压缩结果仍太大时，返回明确错误，不丢弃本轮图片，也不增加隐式重试。

## 旧截图裁剪与重传

仅在历史前缀已超出可发送预算、且显式开启裁剪时执行：

- 只处理边界之前、具有唯一匹配工具调用和结果的旧 `function_call_output` / `custom_tool_call_output` 内联图片。
- 保留所有本轮输入，包括本轮多张截图；不裁剪用户消息图片、URL 或 file_id 引用。
- 从最旧截图开始，按四张一批处理（最后一批可不足四张），目标为总量的 75% 和现有数量限额。
- 图片 part 替换为明确的文字占位符；工具 call_id、结果数组及其他文字保持不变。
- 裁剪后仍无法得到合法历史窗口，则拒绝；不会继续删除受保护内容。
- 单个裁剪检查点最多包含 `MaxRelayImages` 个位置，整条历史继续沿用最多 16 个检查点的边界。

检查点只存原历史前缀摘要与裁剪位置，不存图片、消息或工具参数。先 CAS 保存，再使用处理后的历史；并发冲突会停止本次流程。即使后续生成失败，重试时仍重放相同裁剪，避免客户端继续携带原历史而反复超限。

裁剪与 compact 使用同一条有序检查点链，因此支持“裁剪 → 压缩 → 客户端回传原历史与压缩窗口”的重整。关闭裁剪、关闭提前压缩或把策略设为 `off`，都只停止创建新的转换；已产生的检查点继续识别。

## 检查点升级

新作用域为原账号/API key/会话/model 作用域下的 `/image-history:v2`，不包含策略、张数阈值、预警余量或字节阈值。修改这些值不会丢失已经迁移的新检查点。仍使用原 Redis 存储接口、TTL 和 CAS，不更改 Redis 仓库实现。

启用扩展后首次读取时兼容旧格式：查找当前张数/预警/预留设置对应的原策略 key（并检查 auto_compact/warn），CAS 迁移到稳定 key，保留旧值。**启用扩展后先保持旧阈值完成一次会话请求，再调整阈值**；旧 key 把阈值编码进哈希，没有可反查的会话索引，无法在事先不知道旧阈值时恢复任意历史配置下的 key。

关闭新开关时仍对可信会话做一次 v2 状态探测：存在既有状态则继续兼容已创建的检查点；未找到或探测失败则走原策略，不让关闭状态的普通请求新增缓存故障依赖。原策略自身需要缓存的场景仍按原规则报错。探测失败时只能按客户端原始历史处理，仍受原图片限额保护；已经读到但损坏的 v2 状态不会静默忽略。

建议全部实例升级后再打开新策略。旧版本不理解新增裁剪检查点；回滚程序前应先对受影响会话执行客户端 compact 或结束会话。仅关闭本批开关可继续使用当前版本识别已有检查点。

## 日志和维护接入点

沿用第一批 `bps_request_diagnostics`。新增 `bps_image_budget_compaction`（历史/本轮字节、窗口预算）和 `bps_image_history_trim`（移除数量、剩余字节），均关联现有请求日志上下文，不记录图片内容或参数值。

主要新增模块：

- `image_budget.go`：共享字节计量、预算和结构化超限错误。
- `image_history_trim.go`：纯历史转换、位置检查点与重放。
- `../openai_excel_bps_image_budget.go`：配置读取、稳定状态迁移、分区规划与续接校验。

原有接入点集中于 `attachments.go` / `image_relay.go` 的预算参数包装、`image_policy.go` 的有序裁剪检查点分派，以及主转发的几个调用点。保留原函数入口和默认预算，避免现有调用方整体迁移。

整体复查后，服务层原 `openai_excel_bps_image_policy.go` 与 `setting_excel_bps_image.go` 已恢复为上游版本。扩展配置、状态包装、关闭路径选择和分区规划均在新增 `openai_excel_bps_image_budget.go` 内。默认路径直接调用原策略；扩展路径的稳定状态迁移与分区逻辑独立维护。上游改变图片历史边界、预警或 checkpoint 生命周期时，应同时检查扩展路径与联合测试，不能仅靠 Git 无冲突判断兼容。
